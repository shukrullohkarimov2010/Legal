# Поиск по кодексам Республики Таджикистан

Движок живёт в [`legal_rag.py`](legal_rag.py). `app.py` вызывает его через
`build_rag_chunks`, `tokenize_for_rag` и `retrieve_rag` и не содержит
собственной логики поиска.

## Корпус

|---|---|---:|---:|
| Гражданский | `1918_ru_1.docx` | 1351 | 1368 |
| Уголовный | `574_ru.doc` | 405 | 434 |
| Налоговый | `налоговый кодекс.docx` | 398 | 552 |

Два индекса в `storage/app/rag/`:

* `1918_ru_1.index.json` — только ГК, используется анализом договоров;
* `laws-rt-chat.index.json` — все шесть кодексов, используется чатом.

Третий индекс на диске не лежит: подындекс Уголовного кодекса для страницы
квалификации строится в памяти фильтрацией чатового (`load_crime_rag_index`).

## Как устроен фрагмент

Один фрагмент — одна статья (длинные статьи режутся по границам абзацев).
Фрагмент несёт свои реквизиты, поэтому ссылка на норму собирается из
метаданных, а не вытаскивается регуляркой из текста ответа модели:

```json
{
  "id": "574_ru.doc:247:1",
  "source": "574_ru.doc",
  "code": "Уголовный кодекс Республики Таджикистан",
  "code_short": "УК РТ",
  "chapter": "26",
  "article": "247",
  "article_title": "Мошенничество",
  "title": "Статья 247. Мошенничество",
  "text": "Статья 247. Мошенничество 1) Мошенничество, то есть …"
}
```

В контекст модели уходит строка `ПРОВЕРЕННАЯ ССЫЛКА RAG: Уголовный кодекс
Республики Таджикистан, Глава 26, Статья 247`. Системный промпт разрешает
цитировать реквизиты только оттуда.

Оглавление кодекса отбрасывается: у его строк нет тела между двумя
заголовками статей. Если статья встречается дважды (в оглавлении и в тексте),
остаётся вариант с самым содержательным телом.

## Как считается релевантность

1. **Нормализация.** Стеммер Snowball для русского + отсев служебных слов.
   Реализован внутри проекта: юридический контур обязан работать офлайн.
   Отдельная таблица исключений — разносклоняемые существительные на `-мя`
   («время» / «временем» иначе дают разные основы).
2. **Расширение запроса.** Словарь синонимов переводит разговорную форму в
   формулировку кодекса: «НДС» → «налог на добавленную стоимость»,
   «зарплата» → «заработная плата». Ключи сравниваются по основам.
3. **BM25** по телу статьи и отдельно по названию (вес 2.2).
4. **Покрытие названия.** Если запрос покрыл название статьи целиком —
   сильный бонус: статья «Рабочее время» должна выигрывать у статьи
   «Порядок ведения учёта рабочего времени» на вопрос «что считается
   рабочим временем».
5. **Прямая ссылка.** «статья 214 ГК» поднимает нужную статью бонусом.
6. **Маршрутизация по кодексам.** Мягкие множители (1.30 / 0.88): вопрос про
   увольнение не должен конкурировать с ГК. Маршрутизатор подсказывает, а не
   решает, — вопросы на стыке отраслей не должны терять нормы.
7. **Векторный слой (опционально).** Эмбеддинги Ollama, слияние через
   Reciprocal Rank Fusion. RRF выбран вместо взвешенной суммы: BM25 и косинус
   живут в разных шкалах, и любая нормализация делает вес зависимым от
   конкретной выдачи. Если модель эмбеддингов недоступна, поиск работает
   в лексическом режиме без ошибок.

## Пересборка индекса

```bash
cd python
python build_rag_index.py                # оба индекса
python build_rag_index.py --embeddings   # плюс векторный слой
python build_rag_index.py --check        # проверка без перезаписи
```

Сборка проверяет минимальное число статей на кодекс и пишет через временный
файл: прерванная сборка или сломавшееся извлечение текста не перезапишут
рабочий индекс. Индекс версионирован (`index_version`); при несовпадении
версии `app.py` пересобирает его автоматически.

Векторный слой требует модель эмбеддингов:

```bash
ollama pull nomic-embed-text
```

## Проверка качества

```bash
cd python
python tests/test_legal_rag.py            # модульные тесты движка
python tests/eval_rag.py --ablation       # метрики поиска и вклад компонентов
python tests/eval_rag.py --failures       # какие вопросы не находятся
```

`eval_questions.json` — 47 вопросов, заданных так, как их задаёт человек,
с эталонными статьями. Эталоны сверяются с индексом при каждом запуске:
если статья исчезла из корпуса, метрика об этом сообщит, а не завысит
результат. Оценка офлайновая и не обращается к языковой модели — она меряет
только поиск. Ошибку поиска модель исправить не может: она отвечает по тому,
что ей передали.

Порог приёмки: `Recall@5 ≥ 70%`, иначе `eval_rag.py` возвращает ненулевой код.

## Двуязычный чат: русский и таджикский

`/tasks/chat` отвечает на языке вопроса. Язык определяет `lang_service.detect_lang`
по двум признакам: буквам, которых нет во втором алфавите (`ӣ ӯ ҳ қ ғ ҷ` против
`ы щ ь ц`), и служебным словам — пользователи часто пишут по-таджикски без
диакритики, и тогда работает только второй признак. Локаль страницы уходит на
сервер как значение по умолчанию для случаев вроде «салом», где признаков нет.

Ответ **всегда генерируется по-русски** и переводится, если вопрос был на
таджикском. Так сделано потому, что qwen3:8b таджикский не держит: на прямой
вопрос она срывается в повтор одного токена и выдаёт текст без смысла. Это
проверялось и на генерации, и на переводе готового русского ответа — промптом
не лечится, нужна другая модель.

Переводит NLLB-200-distilled-600M через CTranslate2 в int8: ~620 МБ вместо
~2.4 ГБ у оригинала под torch. Скачивание — `python fetch_translate_model.py`
(докачка при обрыве поддерживается). Без модели слой отключается, и на
таджикский вопрос приходит русский ответ с явной пометкой об этом: молча
отвечать не на том языке нельзя — пользователь решит, что его не поняли.

Два решения, которые важно не сломать при правках:

* **Номера статей проверяются после перевода, а не прячутся до него.** Сначала
  реквизиты маскировались плейсхолдерами — оказалось, это решает не ту задачу.
  Замер на восьми фразах: NLLB иногда просто выбрасывает плейсхолдер, и
  «статье 41» исчезала из ответа целиком; а там, где маска срабатывала, в
  таджикскую фразу вклинивались русские слова («Статья 1 ва статья 250»).
  Без маски модель даёт нормальные термины («моддаи 41», «боби 62») и числа
  переносит верно. Поэтому маскируется только структурная строка
  `ПРОВЕРЕННАЯ ССЫЛКА RAG`, а числа исходника сверяются с переводом
  (`lost_numbers`); потерянное или переписанное словами («5000 сомони» →
  «5 ҳазор сомонӣ») дописывается в скобках. На контрольном наборе 9/9.
* **Аббревиатуры кодексов маскируются, номера статей — нет.** «ТК РТ» NLLB
  превращала то в «Кодекси давлатии меҳнат» («государственный кодекс труда»),
  то в «ТТ»: номер статьи оставался цел, но ссылка вела на несуществующий
  кодекс. Аббревиатуры уходят под маркер и возвращаются дословно; если
  переводчик выбросил и маркер, `repair_citations` дописывает аббревиатуру в
  скобках. На контрольном наборе 6/6, причём случай с потерей маркера там
  реальный — «СК РТ» дописан страховкой.
* **Перевод идёт по предложениям, а не по токенам.** NLLB обучалась на
  предложениях и обрывок фразы переводит мусором. Ответ копится в буфере и
  уходит в чат кусками по границам абзацев и предложений — иначе пользователь
  ждал бы конца генерации молча.
* **Приветствие не поднимает RAG.** «салом» уходило в BM25, цеплялось за
  «салам» — термин исламского финансирования в Налоговом кодексе — и на
  приветствие приходил пересказ статьи 206 о доходах банков. Короткие реплики
  из списка приветствий идут по отдельной ветке: без RAG, без правил
  цитирования и с лимитом 120 токенов.
* **Переведённый запрос дополняется формулировками кодекса.** «бекор карда
  мешавад» NLLB отдаёт как «отменить», и вопрос о трудовом договоре поднимал
  статью 141 Семейного кодекса — об отмене усыновления. `normalize_search_query`
  дописывает к запросу «расторжение прекращение договора», после чего в топе
  оказываются статьи 39, 45 и 42 Трудового кодекса. Словарь синонимов в
  `legal_rag` для этого не годится: «отмена усыновления» и «отмена
  доверенности» — законные термины, связывать «отмену» с «расторжением»
  глобально нельзя.

## Генератор договора на `/contract/create`

`POST /api/contract/draft` **правит разделы уже собранного договора** в два
прохода, а не пишет документ с нуля.

Первый проход — короткий вопрос «какие разделы менять», ответ в десяток
токенов. Второй правит только выбранные. Выигрыш двойной: модель, получив
четыре раздела, переписывала все четыре даже когда критерия было два, а
генерация стоит линейно в токенах вывода и занимает 94% времени запроса.
Менее очевидная часть — первый проход разогревает KV-кэш общего префикса:
промпт правки начинается ровно теми же символами, и разбор запроса
оплачивается один раз на оба прохода. На замере переход от выбора к правке
занимает 8–14 секунд вместо 83.

После правки результат сверяется с формой и критериями, и при расхождении
запускается один повтор по затронутым разделам. В запрос уходят текущие разделы парами «ключ — текст»,
поля формы и критерии пользователя; модель возвращает только те разделы, которые
меняет, и фронт подставляет их по ключу.

Причина — арифметика замеров на этом железе. Генерация занимает 94% времени
запроса и стоит линейно в токенах вывода, поэтому единственный способ ускорить
ответ без смены модели — писать меньше. Полный договор это около 2700 символов
и 591 секунда; правка разделов — 1265 символов и 302 секунды, вдвое быстрее при
том же качестве. Побочные выгоды не менее важны: номер, даты и стороны уходят
из зоны ответственности модели (шапка собирается из формы детерминированно), а
живое превью не приходится замораживать — нетронутые разделы продолжают
следовать за полями формы.

Ключ раздела в разметке ответа (`### payment`) — латиница намеренно: русское
слово модель искажает, на маркере «КРИТЕРИЙ» она уже писала «КРИТИРИЙ». По
ключу выполняется подстановка, так что цена ошибки здесь выше. Если разметки в
ответе нет вовсе, весь текст занимает договор целиком — на случай, когда модель
проигнорировала формат.

Поиск по кодексам строится из типа договора, предмета и критериев — именно они
определяют, какие нормы должны попасть в контекст.

Поля приходят с фронта уже подписанными и переведёнными, парами
«подпись: значение». Бэкенд не знает ни идентификаторов формы, ни локали
интерфейса — иначе эндпоинт пришлось бы править при каждом новом поле в
конструкторе.

Чат на той же странице ходит в обычный `/api/chat`, но с полем `context`:
снимок формы, критерии и текущий текст договора. Без него совет «добавьте
неустойку» не к чему приложить. Модели предписано заканчивать ответ строкой
`КРИТЕРИЙ: ...` — фронт по ней рисует кнопку «добавить в критерии». Разбор
этой строки намеренно устойчив к опечаткам: слово опознаётся по первым
четырём буквам, потому что модель уже писала «КРИТИРИЙ», и строгое совпадение
молча съедало кнопку.

## Оценка риска договора на `/contract/form`

Риски, прошедшие фильтры, складываются не суммой, а как вероятности: каждый
подтверждённый вывод уменьшает «оставшуюся безопасность», поэтому длинный
список не выбивает оценку за 100, а каждый новый пункт её повышает. Потолок —
95: сотня зарезервирована за подтверждённой человеком ситуацией.

Свод оценки в вердикт вынесен в `summarize_contract_risk` — чистую функцию без
RAG, Flask и Ollama. Причина в том, что там легко ошибиться в знаке, а внутри
общего конвейера такую ошибку не проверить. Тесты — `tests/test_risk_metrics.py`.

Ссылка на право другой страны в тексте анализа **не меняет оценку риска**, но
переводит вердикт в «требуется ручная проверка». Раньше за каждое такое
упоминание из оценки вычиталось 20 баллов: чем сильнее модель путалась в
юрисдикции, тем безопаснее выглядел договор, и трёх упоминаний РФ хватало,
чтобы риск 70/100 и «Не подписывать» превратились в 10/100 и «Можно
подписывать». Риск договора не зависит от ошибок разбора — а вот доверять
такому разбору нельзя.

Чек-лист существенных условий учитывает тип договора, но узко: исключения в
`CLAUSES_NOT_APPLICABLE` описывают только случаи, где отсутствие условия
определяет вид договора (дарение безвозмездно, мена — обмен без денежного
расчёта). При слабой уверенности классификатора чек-лист применяется целиком:
пропустить существенное условие опаснее, чем показать лишний пункт.

## Квалификация по УК РТ на `/contract/ugalov-kodex`

Страница отвечает **только** тем, что нашлось в тексте Уголовного кодекса РТ.
Два эндпоинта: `POST /api/crime/search` — поиск норм без модели, и
`POST /api/crime/qualify` — полный разбор; плюс `GET /api/crime/catalog`
для базы знаний.

Кнопка «Найти норму» модель не вызывает вовсе: текст статьи с санкцией — это
уже ответ, и он приходит из индекса дословно и мгновенно.

Разбор отдаётся **потоком NDJSON**: первая строка — опора ответа (статьи, их
тексты и ссылки), дальше токены, последняя — результат сверки ссылок. Ждать
ответ целиком нельзя: страница показывала пустой спиннер и обрывала запрос по
таймауту на пятой минуте («signal is aborted without reason»). Таймаут на
клиенте теперь сторожит только молчание до первого байта.

**`think: false` обязателен.** Модели семейства Qwen3 сначала пишут
рассуждения. Замер на `legal-strong` без этого флага: первый видимый токен
через **705 секунд**, 1928 символов скрытых размышлений, и они же съели лимит
`num_predict` — видимый ответ оборвался на 409 символах. Чат этот флаг ставит,
`send_to_ollama` — нет, поэтому у страницы свой вызов Ollama с `think: false`,
`keep_alive` (иначе каждый запрос заново читает 8 ГБ с диска) и `num_ctx` под
размер промпта вместо объявленных моделью 16k.

**Сигналы жизни.** До первого токена проходят минуты, а молчащее соединение
клиент обрывает: проверка на живом API получила `terminated`, не дождавшись ни
символа. Генерация вынесена в отдельный поток, и пока она молчит, наружу каждые
`CRIME_HEARTBEAT_SECONDS` уходит строка `{"wait": N}` — она держит соединение и
показывает на странице, сколько секунд модель уже думает.

Замеры на прогретой `legal-strong` (описание разбоя, 3 нормы в промпте):
опора ответа на экране — **0,02 с**, первый текст — 100–155 с, весь разбор —
4,8 минуты. Меньшая модель выигрыша не дала: `legal-draft-4b` на том же запросе
отдала первый текст через 35 минут (перечитывание модели с диска съедает больше,
чем экономит меньший размер), поэтому по умолчанию остаётся `legal-strong`,
а `CRIME_MODEL` позволяет сменить её одной переменной.

**Отдельный подындекс.** Поиск идёт не по общему корпусу, а по одному УК РТ:
на «вырвал сумку и убежал» общий индекс поднимал статьи Гражданского и
Налогового кодексов, а уголовной нормы в выдаче не оказывалось вовсе.
Статистика BM25 пересчитывается по одному кодексу — в корпусе из шести
«хищение» и «наказание» частотны настолько, что перестают различать статьи.

**Синонимы решают исход.** Человек описывает событие бытовыми словами, кодекс
оперирует диспозициями. Без пары «вырвал» → «грабеж, открытое хищение чужого
имущества» BM25 не находил ни одной статьи: ни одно слово описания в тексте
кодекса не встречается. Расширение обязано вести и на **название** статьи, а не
только на её определение: по одному «открытому хищению чужого имущества» выше
грабежа (ст. 248) вставали ст. 393 и 337 — у них «хищение» стоит в заголовке и
получает вес названия.

**Порог опоры.** Поиск всегда возвращает лучшее из имеющегося, поэтому
посторонний вопрос даёт формально непустую выдачу. Решает `CRIME_RAG_MIN_SCORE`
(BM25, по умолчанию 8.0): описание преступления даёт 20–130, «какая погода в
Душанбе» — 5 и ниже. Ниже порога модель **не вызывается вообще** — страница
отвечает, что нормы нет. Сгенерированный без нормы текст и есть та выдумка,
ради запрета которой страница переведена на RAG.

**Модель работает в границах выдачи.** В промпт уходит закрытый список
номеров, и ссылки готового ответа сверяются с ним: неподтверждённые статьи
помечаются прямо в тексте (`unverified_articles`). Сверка идёт по отдельной
регулярке — общий `_cited_article_numbers` считает статьёй и «ч. 2», из-за чего
любой ответ с частью статьи помечался бы как выдумка. Текст самой статьи на
страницу уходит из индекса, а не из генерации.

Поиску выдача не режется (`CRIME_RAG_TOP_K`), а в промпт разбора уходит только
`CRIME_QUALIFY_TOP_K` первых норм: разбор запроса стоит линейно в символах
промпта, а ссылалась модель на две-три статьи из восьми.

Локального словаря статей на странице больше нет: он подсказывал правдоподобные,
но чужие номера — «247 — Кража» и «246 — Мошенничество», тогда как в УК РТ
244 — кража, 247 — мошенничество, 246 — хищение кредитных средств.

## Известные ограничения

* Стеммер не сводит отглагольные существительные к глаголу («усыновление» /
  «усыновить») и не справляется с беглой гласной («перевозка» / «перевозок»).
  Частотные пары закрыты словарём синонимов; полное решение — лемматизатор,
  но он тянет внешнюю зависимость.
* Оценочный набор из 47 вопросов мал: метрика показывает направление, а не
  точную величину. Расширение набора — самый дешёвый способ поднять доверие
  к цифрам.
* Кодексы обновляются законами о внесении изменений. Индекс собирается из
  файлов в `storage/app/rag/`; актуальность редакции обеспечивается заменой
  этих файлов, движок её не отслеживает.
* Корпус целиком русский: таджикских текстов кодексов в `storage/app/rag/` нет.
  Таджикский вопрос переводится в русский поисковый запрос, поэтому цитата
  нормы в ответе остаётся русской. Это осознанный компромисс — переведённая
  формулировка статьи перестала бы быть цитатой. Если появятся таджикские
  редакции кодексов, их стоит завести отдельным индексом.
* `nomic-embed-text` в векторном слое обучалась преимущественно на английском.
  На пробной тройке фраз разрыв между близкой и далёкой темой составил 0.04 на
  русском против 0.40 на английском — сигнал на русском корпусе слабый. Это
  одна тройка, а не бенчмарк, но направление стоит проверить на `eval_rag.py`
  перед тем, как полагаться на векторный слой; кандидат на замену — `bge-m3`.

## Извлечение текста из `.doc`

`antiword` без карты кодировки отдаёт кириллицу как `?`: формально успешный
вызов возвращает полмегабайта мусора. `_extract_text_from_doc_command`
перебирает конвертеры и кодировки и отбраковывает результат, в котором доля
кириллицы ниже 30%. Без этой проверки пересборка индекса молча удалила бы
Уголовный кодекс из корпуса.
